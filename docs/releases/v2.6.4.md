# codex-usage v2.6.4

修复上下文压缩请求的 Token 与 API 等价成本未计入统计的问题。

新版 Codex 会把压缩用量写入独立的 `token_usage_record`，但旧 `token_count` 的累计值可能保持不变。旧版扫描器因此遗漏这笔请求。现在按线程和 `response_id` 去重，以 `turn_token_usage` 核对增量；普通响应与压缩请求使用同一计量流程，同 Turn 的旧通知和压缩历史内嵌副本不会叠加计数。

- 保留旧格式 Turn 的累计差分，支持新旧记录过渡、fork 归属、复制恢复、增量扫描和进程重启。
- 有累计但缺少请求明细时补足总量并标记时间归属不确定；身份冲突会回滚当前文件事务，未匹配的旧通知会提示可能缺少尾部用量。
- schema v11 保留旧事件与游标，并要求显式重建后再继续扫描。空数据库可直接使用。模型定价和 Fast 倍率没有变更。

**升级后修正历史：** 先备份统计并确认源 JSONL 仍齐全，再选择 Dashboard 的“重新扫描 → 同意并重建”，或运行 `codex-usage scan --rebuild`。升级程序不会自动重建历史；源文件已经删除、或旧日志未记录实际压缩用量的部分，无法通过重建恢复。

**验证：** 真实数值的四请求回归从旧版的 299,794 修正为 534,532 tokens，差额恰好为压缩请求的 234,738。冻结 46 个本机 rollout 后，仅提取计量元数据进行隔离扫描，5,236 个独立请求、209 个 Turn 的六项 Token 分类全部匹配独立参考值，恢复 50 次压缩的 11,902,610 tokens。另有 85,424 tokens 来自冻结瞬间已写入独立记录、尚未写入旧通知的正常请求。其余旧格式用量与快照一致；重扫新增事件为 0，事件哈希不变，SQLite 完整性检查通过。这是本地用量核对，不是 OpenAI 账单核对。

Fix missing token usage and API-equivalent cost for context compaction requests.

Modern Codex writes compaction usage to independent `token_usage_record` entries while legacy `token_count` totals may remain unchanged. The scanner now deduplicates requests by thread and response ID and reconciles their turn totals. Ordinary responses and compactions share this accounting path; legacy notifications and embedded compaction mirrors do not add the same usage again.

- Retain cumulative differencing for older turns, including mixed-format transitions, fork ownership, restored files, incremental scans and restarts.
- Flag uncertain time attribution when a cumulative record recovers missing request details. Conflicting response identities roll back the file transaction; unmatched legacy notifications expose potentially missing tail usage.
- Schema v11 preserves existing events and cursors until an explicit rebuild. Empty databases work immediately. Model prices and Fast multipliers are unchanged.

**Repair history after upgrading:** back up and verify retained JSONL coverage, then choose **Rescan → Approve and rebuild** or run `codex-usage scan --rebuild`. Updating the binary does not rebuild history automatically. Deleted source files and old compactions without recorded usage cannot be recovered by rebuilding.

**Validation:** the four-request regression now counts 534,532 instead of 299,794 tokens, restoring exactly 234,738 compaction tokens. An isolated accounting-only projection of 46 frozen rollouts matched all six token categories for 5,236 independent requests across 209 turns, recovering 11,902,610 tokens from 50 compactions. Another 85,424 tokens belonged to one ordinary response written before its legacy notification at the snapshot boundary. Other legacy usage matched the retained snapshot. Rescanning inserted zero events and preserved the event hash; SQLite integrity passed. This validates local usage, not account billing.
